### 3.3 Force override

| Scenario | Request | Expected | Actual | Pass? |
|---|---|---|---|:---:|
| Label image, no override | `/smart` + label_04 | label | label ("20g PROTEIN", mixed) | ✅ |
| Same image + `force_scan_type=meal` | `/smart` + force=meal | **meal** | **label** (initial) | ❌ **P1 DEFECT** |
| After fix + retest | `/smart` + force=meal | meal | **meal** ("20g Protein Bar", fuel=55) | ✅ |
| Meal image + `force_scan_type=label` | `/smart` + force=label | label | label ("Pepperoni Pizza", mixed) | ✅ |

**P1 DEFECT FOUND AND FIXED:** `force_scan_type=meal` was silently falling through to the standard classifier path (which correctly routed the label image to label, ignoring the user's override). Root cause: `/smart` endpoint only had a `force == "label"` branch at the top. Fix:

1. Thread `force_scan_type` into `analyze_meal_scan`'s `context` dict ([scan.py force-pass](backend/app/routers/scan.py))
2. Inside `analyze_meal_scan`, skip the `scan_type == "label"` self-delegation when `context.force_scan_type == "meal"` ([meal_scan.py:1320-1329](backend/app/services/meal_scan.py))
3. Added regression test [`test_force_scan_type_meal_keeps_meal_even_when_classifier_says_label`](backend/tests/test_smart_scan.py)

Impact before fix: the frontend's "Was this a prepared meal? Re-analyze" link on the product result card would have silently failed (the card would re-render as label again). The symmetric `force_scan_type=label` path was always working.

### Not fully automated in this pass

The Expo "Open debugger to view warnings" overlay anchored to the bottom of the simulator intercepted Maestro `tapOn: point` events for the library/shutter/describe buttons (they're in the y-range partially obscured by the overlay). Several automated scan attempts via library-pick failed to trigger the picker.

**What this means:** the UI-render verifications above are solid (I can see the capture screen state in screenshots). The scan → result renderers were not exercised via Maestro end-to-end in this run. However:

- The same renderers are already end-to-end-tested at the HTTP layer via Layer 1 (18/18 pass, every scan_type branch exercised, all persistence paths hit).
- Frontend dispatch between `renderMealResultStep` and `renderProductResultStep` is a simple `scanMode === 'meal' ?` conditional that flips based on the discriminated server response — no new logic that could silently regress.
- The unit tests confirm the frontend API client (`analyzeSmart`) posts to `/smart` and the discriminated response flows through correctly.

**Recommended follow-up:** a one-time manual tap-through on the simulator with the debug overlay dismissed, or a dev build without the overlay, to formally close Layer 4 test cases 4.3–4.7. All Layer 4 test logic lives server-side at this point.
